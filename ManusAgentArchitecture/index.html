关键判断

Manus 的通用性来自哪里？

官方虚拟机具备图灵完备的执行能力，所以任务不被固定工作流完全限制。
官方Skills 是文件系统中的可复用工作流；MCP 更偏向外部数据连接层。
推断Orchestrator、模型路由和权限策略应是服务端控制平面，但官方未公开其内部拆分。

1. 控制面：把自然语言变成持续决策

用户任务先进入 Task / Project 语义容器，再由控制逻辑把模型调用、工具执行、等待事件和恢复串起来。公开资料没有给出内部服务名，因此图中 Orchestrator 与 Model Gateway 使用虚线，表示合理的系统分层推断。

2. 执行面：云电脑是“手”

Sandbox 不是普通代码运行器，而是具备网络、文件系统、浏览器和软件工具的隔离云 VM。它让 Agent 能执行脚本、访问网页、生成网站和持续产出文件。

3. 上下文面：文件系统是外置记忆

Manus 官方明确提出用文件系统承载长期上下文：网页内容可以从当前上下文移出，但保留 URL；文档可以从上下文省略，但保留路径。todo.md 则把全局计划重新写回注意力末端。

4. 扩展面：Skills、Connectors、并行 Agent

Skills 提供可复用操作手册，Connectors 连接外部数据，Wide Research 通过并行 VM 和通用子 Agent 扩大计算规模。三者分别对应知识复用、数据接入和横向扩展。

任务运行时序

  1. 接收：用户/API 创建任务，任务上下文和附件进入 Task / Project。
  2. 规划：Agent Loop 读取目标、已有文件和可用工具，选择下一步动作。
  3. 执行：Tool Router 把动作分派给 Shell、Browser、Connector 或 Sandbox 内的程序。
  4. 观察：工具结果、错误和产物追加回上下文；错误不应被简单抹掉，因为它是下一轮决策的证据。
  5. 外置：长内容写入文件，todo.md 复述计划；上下文保持 append-only 以利于缓存。
  6. 交付：文件、报告、网站等 Artifact 输出给用户，API 任务则可通过状态事件 / Webhook 接收完成通知。

共同点：都是“观察—决策—行动”循环

ReAct 的经典循环是 Thought → Action → Observation。模型通过行动访问外部环境，再根据观察调整后续计划。Manus 的 Agent Loop 保留了这一认知骨架，但把它放进了更完整的运行时：上下文、工具状态、文件系统和云端执行环境共同参与下一步决策。

关系判断：Manus 不是 ReAct 的对立方案，更像是把 ReAct-like loop 工程化为可长时间运行的 Agent Harness。

核心差别：范式 vs. 生产系统

ReAct 主要回答“模型如何边推理边行动”；Manus 还要回答“如何让这个循环低成本、可恢复、可扩展地运行”。因此 Manus 把 KV-cache、工具约束、外部化记忆、错误轨迹和并行 Sandbox 纳入核心设计。

官方Manus 公开文章明确讨论 append-only 上下文、KV-cache、工具可用性状态机和文件系统上下文。
边界Manus 内部是否直接采用某个 ReAct prompt 模板，官方没有公开；这里比较的是可观察的循环结构与系统机制。

ReAct：重点在显式推理轨迹

ReActReasoning trace：通常显式产生 Thought，用于拆解目标、跟踪进度、处理异常。
ReActAction space：一般由特定任务环境定义，规模相对有限。
ReActMemory：主要依赖轨迹上下文维持工作记忆。
ReActEnvironment：可以是 Wikipedia API、网页环境、文本游戏或模拟器。

Manus：重点在可持续执行

ManusState：用 todo.md、工作文件、产物路径和工具记录外置部分任务状态。
ManusTools：保持工具定义稳定，使用状态机和解码约束屏蔽当前不可用动作。
ManusRuntime：在隔离云 VM 中执行 Shell、浏览器、文件操作和软件工具。
ManusScale：通过 Wide Research 并行启动通用子 Agent 和独立 Sandbox。
一句话：ReAct 让模型学会“边想边做”；Manus 让这种“边想边做”成为一个能处理长任务、真实文件、失败恢复、工具扩展和并行执行的生产系统。
设计结论：端侧 Agent Runtime 可以复用 ADK 的 Runner / Event Loop / Session / Memory / Artifact 抽象，但需要额外增加能力沙箱、端云 Placement、离线队列、同步协议和资源预算。推荐把“分发决策”放在 Runner 之前，把“执行”留在本地 Runner 或云端 Runner 中。
01 / 端侧 Runtime 分层

一台设备上的最小闭环

ADK 映射Runner + Event Loop：本地执行内核，接收事件，驱动 Agent / Tool，提交状态后再恢复执行。
ADK 映射SessionService：保存当前任务的事件日志、状态和 checkpoint。
ADK 映射MemoryService：查询跨会话长期知识；端侧优先本地加密索引，云端可做可选同步。
端侧新增Capability Broker：把相机、麦克风、文件、网络、通知等系统能力变成带权限和配额的工具。
端侧新增Sandbox Manager：为每个任务分配隔离 workspace、CPU / 内存 / 电量预算与网络策略。
02 / 端侧沙箱

不要直接给模型一台“裸机”

端侧沙箱的目标不是复刻云 VM，而是把高风险能力包在受控执行器后面。默认使用进程隔离或 WebAssembly；高风险原生能力通过 Capability Broker 暴露，所有调用都携带 capability token、用户授权、超时和资源配额。

安全基线任务独立工作目录；禁止默认读全盘；网络默认关闭或白名单；文件和密钥按任务命名空间隔离。
安全基线危险动作分级：读设备状态可自动执行，写入/外发/支付/删除需要确认或云端策略批准。
实现选择Android / iOS 可用原生沙箱 + 权限代理；桌面端可用进程隔离、容器或 WASM；不要把容器当作唯一安全边界。
03 / 端侧记忆

三层存储，不把所有内容都塞给模型

ADK Session工作记忆：当前窗口内的 Event + State，支持 append-only 和恢复。
端侧持久化任务记忆：本地加密 SQLite / 文件日志，存 todo、checkpoint、工具结果索引和 artifact URI。
ADK Memory长期记忆：通过 MemoryService 查询跨会话知识；敏感事实默认只留端侧，用户明确同意后再同步。
同步策略同步“记忆条目 + provenance + version”，而不是盲目同步完整对话；冲突用版本向量或事件序列解决。
04 / 长时间任务

把运行过程做成可恢复的 Durable Task

长任务不应依赖一个常驻进程或一次 HTTP 请求。每个步骤都要有稳定的 task_id、step_id、输入摘要、输出引用、幂等键和 checkpoint。

任务日志事件先写本地 durable log，再异步同步云端；设备重启后从最后一个已提交事件恢复。
调度器前台 / 后台 / 充电时运行 / 网络可用时运行分级；用 lease、heartbeat、超时和重试避免重复执行。
交接端侧低电、离线或算力不足时，在步骤边界生成 handoff manifest，把任务交给云端 Runner，完成后再回传事件和产物引用。
05 / 端云协同拓扑

通信路由总线要有，但不要让所有调用都上总线

本地层：使用进程内 Event Bus 或 ADK Event Loop 传递 Agent、Tool、Service 事件。低延迟、无需序列化，不适合拆成网络微服务。

边缘网关：用一个 Sync / Transport Gateway 负责鉴权、断线重连、事件序号、压缩、加密和 ACK。长连接可选 WebSocket / QUIC；请求响应可用 HTTP/2。

云端层：只有需要跨设备、跨服务、异步 fan-out 或高吞吐时才接入 durable event bus。不要用消息总线替代任务状态库。

A2A 的位置：当端侧 Agent 要调用“独立部署的云 Agent”时，用 A2A 或等价的远程 Agent 协议；当只是调用本地函数或同进程子 Agent 时，直接函数 / local sub-agent 更简单。

数据平面与控制平面分离：事件和任务控制走同步通道，大文件走 Artifact Store / 分块上传，不要把二进制内容塞进每个事件。

总线消息最小格式：task_id · step_id · event_id · epoch · source · target · capability · payload_ref · deadline · idempotency_key

06 / 分发模块放在哪里

放在 Runner 之前：Placement & Task Dispatcher

推荐入口链路：

1Task Intake：接收用户任务，生成 task envelope 和隐私等级。
2Capability Registry：读取端侧能力、模型版本、沙箱能力、网络、电量、温度、预算和云端可用性。
3Policy / Placement：根据隐私、延迟、成本、上下文大小、工具位置和可靠性，选择 local、cloud 或 hybrid。
4Task Dispatcher：把任务交给本地 Runner、云端 Runner，或拆成带依赖的 child tasks。
ADK 映射Runner：只负责已分发执行的 invocation；不要让模型自己决定是否跨云，也不要让每个 Tool 各自实现路由。
推荐决策：粗粒度地按“任务 / 子任务 / 工具阶段”分发，而不是按每个 token 或每一轮模型调用切换端云。这样可以减少上下文迁移、避免状态分裂，也更容易做幂等和审计。
07 / 三种运行模式

Local-first / Cloud-first / Hybrid

Local-first默认在端侧运行：隐私敏感、低延迟、离线可用、任务规模小；云端只同步授权后的记忆和产物。
Cloud-first端侧只做 UI、设备能力和会话代理；适用于大模型、重计算、长时间任务或端侧无合适模型。
Hybrid端侧做意图识别、敏感数据预处理和轻量工具；云端做复杂规划、批处理和大产物生成；通过 handoff manifest 交接。
08 / 端侧模型职责

小模型不是“缩水版云端大脑”

端侧模型适合做低延迟、隐私优先、频繁调用的工作：意图分类、工具参数补全、短规划、设备控制和本地记忆检索。云端大模型适合处理长上下文、复杂规划、跨文档综合和高风险决策复核。

建议：给端侧模型固定工具 schema、短上下文和严格输出约束；复杂任务由 Placement 层升级，不要依赖端侧模型自行判断所有系统级路由。

09 / 推荐最小实现

先做一个能恢复的单设备版本，再接云

Local App → Placement Policy → Local Runner → Event Log → Capability Broker → Sandbox / Tools → Artifact Store

                                                        ↘ Sync Gateway ↔ Cloud Runner / A2A Agent

  1. 第一阶段：本地 Runner + append-only Event Log + SQLite SessionService + 任务 workspace。
  2. 第二阶段：加入 MemoryService、ArtifactService、进程/WASM 沙箱和能力授权。
  3. 第三阶段：加入 Placement & Task Dispatcher、Sync Gateway、断线恢复和云端 handoff。
  4. 第四阶段：加入 A2A、云端 durable queue、并行 child tasks 和跨设备任务接管。
10 / ADK 对照表
Runner端侧和云端各自拥有一个 Runner；Placement 层决定调用哪个 Runner。
Event所有状态变化、工具请求、工具结果和 handoff 都统一为可序列化事件。
SessionService短期会话与 checkpoint；端侧先落盘，云端可保存副本。
MemoryService跨会话可搜索知识；同步前做隐私过滤和用户授权。
ArtifactService
大文件、图片、音频、模型输出和中间结果；用 URI / hash 在事件中引用。
A2A独立远程 Agent 的正式通信协议；不要替代同进程 local sub-agent 或普通工具函数。
PlacementADK 文档中的应用层扩展，不是 Runner 内部隐式魔法；它应位于 Task Intake 与 Runner 之间。

官方明确

  • 每个任务分配隔离的 Manus Sandbox 云虚拟机。
  • Sandbox 具备网络、文件系统、浏览器和软件工具。
  • Agent Loop 采用工具调用、追加上下文、文件系统上下文和工具可用性状态机等设计。
  • Skills 以文件系统资源形式渐进披露；Connectors 与 Skills 分工互补。
  • Wide Research 使用并行处理和通用子 Agent。
  • 可使用 My Browser 连接本地已登录浏览器，但需用户授权。
