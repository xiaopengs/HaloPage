## 一、发布策略

### 1.1 版本号规范

- **格式**：语义化版本 `主.次.修订`（如 `1.0.0`），与 Git Tag 一一绑定：`v1.0.0`。
- **升版规则**：大功能或破坏性变更升主版；常规功能（V1.1 的学科自定义/完成统计等）升次版；缺陷修复升修订（如 `1.0.1`）。
- **可追溯**：每次发布记录"版本号 + git commit + 构建时间 + 制品位置 + 上一稳定版本位置"，缺一不可追溯。
- **制品命名**：`homework-tracker-server-{版本}-{commit短sha}.tar.gz`、`homework-tracker-client-{版本}-{commit短sha}.tar.gz`；前端构建注入 `VITE_BUILD_VERSION`（版本+commit），错误上报与页面页脚可定位版本。
- **兼容承诺**：服务端接口对新旧客户端向后兼容至少 2 个版本（Web 端体现为"发布后旧静态资源缓存仍可用 + API 不破坏性变更"）。

### 1.2 发布节奏与发布窗口

| 项 | 规则 | 依据 |
|---|---|---|
| 迭代节奏 | Web 无商店审核，可高频发布；建议每周 ≤2 次常规发布；V1.1/V1.2 攒批发布 | 手册第九章（Web 更新灵活） |
| 版本节奏 | V1.0 MVP 首发 → 72h 观察 → V1.1（上线后第 2~6 周）→ V1.2+（Q+1） | PRD 版本路线图 |
| **发布时间窗** | **工作日上午 10:00-11:00 发布，留足当天观察与响应时间；严禁 19:00-22:00 发布** | 家长核心使用时段为晚间放学后（选型报告核心场景），此窗口发布会直接冲击业务高峰 |
| 数据库迁移窗口 | 仅随版本发布执行，且只做向后兼容变更（先加后删） | 手册基础流程 + 5.3 |
| 强更策略 | 仅"安全/合规/阻断性缺陷"使用强制刷新（Web 端=清理缓存引导）；其余软引导 | 手册第九章 |
| 避开 | 节假日、学校开学首周等峰值期不做重大变更 | 手册第九章 |

### 1.3 环境划分（必备四套，配置与密钥按环境隔离）

| 环境 | 用途 | 配置 | 数据 | 部署触发 |
|---|---|---|---|---|
| 开发（local） | 研发自测 | Docker MySQL（docker-compose）+ Mock AI Provider | 假数据/造数脚本 | 本地 |
| 测试（staging） | QA 全量/兼容/性能/安全测试 | 类生产配置；独立子域名 + HTTPS；OSS 独立 Bucket；AI 走测试 Key 或 Mock 开关 | 脱敏造数（≥5000 条作业、≥10 孩子、跨 8 周） | CI 自动（main 合并即部署） |
| 预发（pre-prod） | 发布前最终验证（UAT/验收） | 与生产同配置、同版本制品、同 Nginx/PM2 形态；**禁止同步生产真实儿童数据，仅脱敏数据或空库** | 脱敏子集 | 人工触发 |
| 生产（production） | 正式服务 | 生产密钥（环境变量注入，不入库） | 真实数据（监护人代理模式） | 人工审批 + tag 触发 |

**环境隔离红线**：生产密钥只存在于生产服务器与 CI 的 production environment secrets；staging/pre-prod 使用独立 Bucket、独立数据库实例（或独立 schema）、独立 API Key；四套环境配置分离，禁止一套 .env 通用。

## 二、CI/CD 流水线设计

### 2.1 流水线总览与关键卡点（按手册基础流程，卡点不省略）

```
代码提交/PR → 代码检查（Lint+TypeCheck）→ 单元测试 → 接口冒烟集（Provider Mock）
   → 构建（前端 Vite + 后端 tsc）→ 制品打包（带版本号+commit，上传制品库）
   → 自动部署【测试环境】→ 冒烟通过 → 自动化回归（接口冒烟+契约）
   → 人工确认 → 部署【预发环境】→ 验证（脱敏数据 UAT）
   → 发布审批（production environment 审批人）→ 部署【生产】（灰度/分批）→ 全量
```

关键卡点（任一不过，禁止流入下一环节）：

1. **Lint/TypeCheck/单测/接口冒烟失败 → 构建不产出、不部署**；
2. **制品唯一**：生产运行的包必须来自 CI 产出的同一制品（按 commit 校验），禁止本地打包直传生产；
3. **版本号规范**：每次发布 `主.次.修订` + git commit 可追溯；
4. **回滚制品保留**：至少保留上一稳定版本制品（CI 制品库保留最近 10 个版本 + 服务器本地保留上一版本目录），随时可切回；
5. **数据库迁移卡点**：`prisma migrate deploy` 随部署脚本执行，CI 中已对测试库演练过同一迁移文件；迁移含破坏性变更（DROP/改类型）时流水线直接失败（由规范约束，见 3.6）。

### 2.2 GitHub Actions 配置要点（YAML 骨架）

> 仓库 prerequisites：代码入库即初始化 Git 仓库 + `main` 主干保护（PR 合入、CI 绿灯、至少 1 人 review）。技术栈 Node.js 20 + pnpm ≥8，monorepo（server/ + client/）。

```yaml
name: ci-cd
on:
  push: { branches: [main] }
  pull_request: { branches: [main] }
  push: { tags: ['v*'] }          # 生产发布走 tag 触发
  workflow_dispatch:              # 预发/生产手动触发

env:
  NODE_VERSION: '20'
  APP_VERSION: ${{ github.ref_type == 'tag' && github.ref_name || github.sha }}

jobs:
  quality:                        # 卡点 1：代码检查 + 测试
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'pnpm' }
      - run: pnpm install --frozen-lockfile
      - run: pnpm -r lint                      # ESLint + Prettier check
      - run: pnpm -r typecheck                 # tsc --noEmit（strict）
      - run: pnpm -r test:unit                 # vitest：周一起算/状态机/压缩计算/限流
      - run: pnpm --filter server test:smoke   # 接口冒烟（Mock Provider），失败即阻断

  build:                          # 卡点 2：构建 + 制品唯一
    needs: quality
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'pnpm' }
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter client build
        env: { VITE_BUILD_VERSION: '${{ env.APP_VERSION }}+${{ github.sha }}' }
      - run: pnpm --filter server build
      - name: 打包制品（版本号+commit）
        run: |
          tar czf server-${APP_VERSION}-${GITHUB_SHA::7}.tar.gz -C server dist prisma
          tar czf client-${APP_VERSION}-${GITHUB_SHA::7}.tar.gz -C client dist
      - uses: actions/upload-artifact@v4       # 制品库，保留最近 10 个
        with: { retention-days: 30, path: '*.tar.gz' }

  deploy-staging:                 # 自动部署测试环境
    needs: build
    if: github.ref == 'refs/heads/main'
    environment: staging
    steps:
      - uses: actions/download-artifact@v4
      - name: SSH 部署 staging（rsync + migrate + reload）
        run: |
          rsync -az server-*.tar.gz deploy@staging:/opt/homework-tracker/releases/
          ssh deploy@staging '
            cd /opt/homework-tracker/releases && tar xzf server-*.tar.gz -d  # 解包到版本目录
            cd server && pnpm i --prod --frozen-lockfile
            npx prisma migrate deploy           # 卡点：迁移失败则发布失败
            pm2 reload homework-tracker --env staging'
      - name: 冒烟（health + 5 条核心接口）
        run: ./scripts/smoke.sh https://staging.example.internal

  regression:                     # 自动化回归（含契约测试）
    needs: deploy-staging
    steps:
      - run: pnpm --filter server test:api     # 接口回归 + OpenAPI 契约测试（≤10 分钟）

  deploy-preprod:                 # 人工确认后部署预发
    needs: regression
    if: github.ref == 'refs/heads/main'
    environment: pre-prod         # 需审批人确认
    steps: [同上部署步骤，target=pre-prod, environment= pre-prod]

  deploy-production:              # 卡点：发布审批 + tag 触发 + 灰度
    needs: [deploy-preprod]
    if: startsWith(github.ref, 'refs/tags/v')
    environment: production       # GitHub Environment 配置 required reviewers
    steps:
      - name: 灰度 5%（白名单+比例分流开关）
        run: ./scripts/release.sh canary 5
      - name: 观察 ≥30min 指标后人工放量 50% → 100%
        run: ./scripts/release.sh promote --step 50   # 二次审批
```

**配置要点清单**：

| 要点 | 做法 |
|---|---|
| 依赖缓存 | `actions/setup-node` 的 pnpm cache + `--frozen-lockfile`（lockfile 漂移即失败） |
| 密钥管理 | GitHub Environments + Environment Secrets：`staging`/`pre-prod`/`production` 各自独立 secrets；CI 中不落盘明文（SSH key 用 secrets，部署机授权 CI 专用 deploy 账号，仅开放 `/opt/homework-tracker` 写入与 `pm2 reload` 权限） |
| 制品唯一性校验 | 部署脚本校验制品名中的 commit 与当前 tag 一致，不一致拒绝部署 |
| 迁移卡点 | `npx prisma migrate deploy` 失败 → 发布失败、保留现场、不回滚数据（见 5.3） |
| 灰度开关 | 服务端按 user_id 哈希取模分流（0-99 → 新版本）；白名单表/配置先行；前端用 CDN 版本目录切换（见 5.1） |
| 通知 | 部署结果推送企业微信/邮件；失败自动 @发布负责人 |

### 2.3 制品管理

- 制品内容：前端 `dist/`（含 `index.html` + hash 静态资源）、后端 `dist/` + `prisma/`（schema + migrations）+ `package.json` + `ecosystem.config.cjs`。
- 存放：CI 制品库（保留 30 天/最近 10 个）+ 服务器 `/opt/homework-tracker/releases/{版本}/`（本地保留上一稳定版本，用于 5 分钟级回滚）。
- 每次发布归档制品记录：版本号、commit、构建时间、制品位置、上一稳定版本位置（手册第十二章）。

### 2.4 密钥在 CI 中的管理（密钥不入代码库）

- 禁止：任何密钥、Token、AccessKey、`.env.production` 提交进仓库；`.gitignore` 显式忽略 `.env*`、`*.pem`、`*.keystore`。
- CI 侧：GitHub Environment Secrets 按环境隔离；仓库开启 secret scanning + push protection；每次发版前跑 `gitleaks detect` 作为流水线卡点（发现历史泄露立即轮换该密钥）。
- 运行侧：生产密钥仅存于服务器环境变量文件（权限 600、属主 deploy）或云 KMS 注入（见 3.5）。

## 三、部署方案

### 3.1 部署方案选型（对照手册三方案对比）

| 方案 | 优势 | 劣势 | 适用 | 本项目判断 |
|---|---|---|---|---|
| 云服务器（ECS） | 完全可控、成本可预估、架构已被技术方案选定 | 需自运维、扩容要操作 | 常规业务、有运维能力 | **选定**：技术研发方案 §1.2 已定"单台 4C8G + Nginx + PM2 双实例"，支撑 500 并发；OSS 直传不依赖厂商 Serverless；日活千级单机足够 |
| Serverless（函数/云托管） | 免运维、弹性 | 冷启动、长任务受限（识别链路最长 60s 分级超时）、锁定风险 | 流量波动大、小团队 | 不选：识别降级链为长时分级任务，进程内异步 + DB 状态机在 Serverless 下语义复杂化 |
| 静态托管（OSS+CDN） | 极廉价、高可用、秒级发布 | 仅前端/静态 | 官网、纯前端 | **部分采用**：前端静态资源走 CDN + 版本目录，作为灰度与秒级回退手段（5.1） |

**组合基线落地**：后端 Node.js 部署云服务器（PM2 双实例）；前端静态资源 CDN 分发；MySQL 8 云数据库（初期可与服务器同机，V1.2+ 迁云 RDS）；阿里云 OSS 私有 Bucket 存照片。运行成本约 200~1000 元/月（选型报告口径）。

### 3.2 部署架构（承接技术方案拓扑）

```
家长（手机/桌面浏览器）── HTTPS(TLS1.2+) ──▶ CDN（静态资源/图片缩略图）
                                        └─▶ Nginx（HTTPS 终止 + 静态 + 限流兜底）
                                              └─▶ PM2 cluster（2 实例）── Express + TS
                                                    ├── /api/v1/*（JWT 鉴权 + 水平越权校验）
                                                    └── 识别执行器（分级超时 + 降级链）
                                              ├── MySQL 8（每日 03:00 mysqldump → OSS，保留 14 天）
                                              ├── 阿里云 OSS 私有 Bucket（STS 直传，签名 URL 读）
                                              └── Qwen-VL / GPT-4o·Claude / 百度 OCR / Sentry
```

### 3.3 服务器部署细则（Nginx + PM2 双实例）

**Nginx 关键配置**：

```nginx
server {
  listen 443 ssl http2;
  server_name app.homework.example.com;            # C 端 + 后台同站
  ssl_certificate     /etc/letsencrypt/live/app.homework.example.com/fullchain.pem;  # 证书链完整
  ssl_certificate_key /etc/letsencrypt/live/app.homework.example.com/privkey.pem;
  ssl_protocols TLSv1.2 TLSv1.3;

  # 安全响应头
  add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
  add_header X-Content-Type-Options nosniff always;
  add_header X-Frame-Options DENY always;

  gzip on; gzip_types text/css application/javascript application/json image/svg+xml;

  # 前端静态资源（SPA）
  location / {
    root /opt/homework-tracker/client/dist;
    try_files $uri $uri/ /index.html;
    location ~* \.(js|css|png|jpg|svg|woff2)$ {
      expires 30d; add_header Cache-Control "public, immutable";   # Vite hash 文件名
    }
  }

  # 后端 API
  location /api/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    client_max_body_size 6m;                      # 服务端代理上传降级通道（≤5MB + 余量）
    limit_req zone=api burst=20 nodelay;          # 全局限流兜底（应用层另有 100 req/分/IP）
    proxy_read_timeout 35s;                       # 覆盖识别前端 30s 上限
  }

  # 管理后台访问控制（见 4.3）
  location /admin {
    allow 办公网段/固定IP;  deny all;             # IP 白名单
    root /opt/homework-tracker/client/dist;
    try_files $uri $uri/ /index.html;
  }
}
server { listen 80; server_name app.homework.example.com; return 301 https://$host$request_uri; }
```

### 3.4 HTTPS 证书

| 项 | 方案 |
|---|---|
| 证书来源 | Let's Encrypt（免费，技术方案口径）；`certbot --nginx` 签发 |
| 覆盖域名 | C 端主域 + `www` + 管理后台同域路径（若后台独立子域须一并加 SAN）——**多域名漏配是高频坑** |
| 证书链 | 必须使用 `fullchain.pem`（链不完整会导致部分安卓机/微信 WebView 报错） |
| 自动续期 | `certbot renew` 加入 crontab（每日 03:30 dry-run 检查、到期前 30 天自动续）；**到期监控：证书剩余 <30 天触发告警（联动 Phase 4 运维）** |
| 沙盒环境 | 拍照链路要求安全上下文（相机权限在非安全上下文被拦截，选型报告 3.4）→ 沙盒也必须 HTTPS：内网用 `mkcert` 本地 CA 自签名（验收机需安装 CA 根证书）或有公网 IP 时用真实域名 + Let's Encrypt；**禁止沙盒用裸 HTTP 验收拍照链路** |

### 3.5 环境变量与密钥管理

**原则**：密钥不进代码库；生产配置与开发隔离；密钥仅存环境变量（服务器文件权限 600 / 云 KMS / CI Environment Secrets）；定期轮换。

**密钥清单（按环境隔离，逐一在检查清单核验）**：

| 变量 | 用途 | 环境 |
|---|---|---|
| `NODE_ENV` / `PORT` | 运行模式 / 端口 | 全部 |
| `DATABASE_URL` | MySQL 连接（含密码） | 按环境 |
| `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` | 双 Token 签发 | 按环境（生产独立） |
| `PHONE_ENC_KEY` | 手机号 AES-256-GCM 主密钥 | 按环境（**泄露=儿童/家长隐私事件，最高敏感**） |
| `OSS_ACCESS_KEY_ID/SECRET`、`OSS_BUCKET`、`OSS_REGION`、`OSS_RAM_ROLE` | OSS 私有桶 + STS 直传 | 按环境（staging 独立 Bucket） |
| `DASHSCOPE_API_KEY` | Qwen-VL 主链路 | 按环境（staging 用测试 Key/Mock） |
| `OPENAI_API_KEY`（可选） | 备用 LLM | 按环境 |
| `BAIDU_OCR_KEY/SECRET`（可选） | 降级 OCR | 按环境 |
| `SENTRY_DSN` | 前端错误监控 | 按环境 |
| `ADMIN_INIT_*` / `ADMIN_IP_WHITELIST` | 管理后台初始账号与白名单 | 仅生产 |
| `RECOGNITION_RATE_LIMIT` 等限流参数 | 风控阈值 | 按环境 |

**泄露防控**：`.gitignore` 忽略 `.env*`；CI 卡点 `gitleaks detect`； secret scanning + push protection；疑似泄露 → 立即轮换对应密钥（OSS AccessKey/JWT Secret 可热轮换，轮换后旧 Token 自然过期）。

### 3.6 数据库迁移（Prisma migrate）

| 规则 | 说明 |
|---|---|
| 迁移入口 | `npx prisma migrate deploy`（生产禁 `migrate dev`；禁手写 SQL 直改结构） |
| 变更纪律 | **只做向后兼容变更**：新增列/表 = 先加（新代码兼容旧结构读不到时给默认值）；删除列/改类型 = 分两个版本（本版本加新的，下版本删旧的）；禁止一次发布内"先删后加" |
| CI 演练 | 同一 migration 文件必须已在 CI 对测试库 `migrate deploy` 成功，方可进生产（卡点） |
| 失败处置 | 迁移失败 → 发布中止、保留现场、DB 不回流旧版本数据（新迁移若已部分生效，按"先加后删"原则新代码仍兼容）；人工介入评估，禁止自动 down |
| 种子数据 | subjects 预置（语文/数学/英语/科学/道德与法治/其他）通过 migration 的 seed 脚本幂等执行 |
| 备份先行 | 每次 `migrate deploy` 前强制 `mysqldump`（见 3.3 步骤 2），备份文件留存 14 天（OSS） |

### 3.7 备份与恢复（承接技术方案 §7.3）

- 每日 03:00 `mysqldump` 全量 → OSS，保留 14 天；
- 每季度恢复演练一次（验证备份可用，演练记录归档）；
- RPO = 24h（每日全量）；发布窗口增量风险由"只增不破坏"迁移纪律 + 软删除设计兜底；
- 照片数据在 OSS（私有桶），删除走服务端 objectKey 物理删除（注销流程 30 天内完成）。

## 五、灰度发布与回滚方案

### 5.1 灰度策略

| 阶段 | 放量 | 准入条件 | 观察指标（每阶段 ≥24h，异常即暂停） |
|---|---|---|---|
| 种子验证 | 白名单 5~10 个家长账号（内部/亲友） | 预发 UAT 通过 + 团长回访清单通过 | JS 错误率、5 条核心链路、识别成功率 |
| 灰度 5% | 用户 ID 哈希取模 0-4（新版本服务端） | 种子期 0 P0/P1 | 接口错误率 <1%、上传成功率 ≥99%、注册→首条作业转化 ≥60%、识别确认率 ≥70% |
| 灰度 50% | 取模 0-49 | 5% 阶段指标全部达标 | 同上 + WAP 无异常下跌 |
| 全量 100% | 全部用户 | 50% 阶段达标 | 72h 观察（第八章） |

**各端灰度手段**（对照手册）：

| 端 | 手段 | 回退速度 |
|---|---|---|
| 服务端 | PM2 双实例按 user_id 取模分流（或双版本目录 + Nginx weight）→ 白名单 → 5% → 50% → 全量 | 分钟级 |
| Web 前端 | CDN 版本目录切换（`/v1.0.0/index.html` 切流） | **秒级** |
| 管理后台 | 与 C 端同版本发布，白名单账号先行 | 分钟级 |

**首发说明（直接全量的理由）**：V1.0 为首发冷启动、无存量用户，按手册纪律可说明后直接上线——但为控制儿童数据合规与体验风险，仍以"种子白名单验证 1~3 天 → 全量"两段式执行，不等同于无灰度裸发。**V1.0 之后的每次有存量更新，默认按上表五阶段灰度，直接全量需发布负责人书面说明理由并获团长批准。**

### 5.2 回滚方案（手册模板，必填可执行）

```
【回滚触发条件】（满足任一即触发，发布负责人决策，5 分钟内启动）
  1. 核心接口错误率 >1% 持续 5 分钟
  2. 出现 P0 bug：白屏/数据丢失/儿童数据泄露/主流程阻断
  3. 前端 JS 错误率 >0.5% PV（Sentry）或白屏/卡死率 >0
  4. 核心转化（注册→首条作业入库）跌幅 >20%
  5. 上传成功率 <99% 或识别全链路不可用 >30 分钟（先关识别入口转手动兜底，仍恶化则回滚）
  6. 安全事件：疑似越权/数据泄露/密钥泄露

【回滚步骤】
  1. 服务端（预计 5~10 分钟）：
     ln -sfn /opt/homework-tracker/releases/{上一稳定版本} /opt/homework-tracker/current
     pm2 reload homework-tracker --env production      # 或 pm2 deploy 执行 revert
     验证：curl https://域名/api/v1/health + 5 条核心接口探活
  2. Web 前端（秒级）：
     CDN/Nginx 静态目录切回上一版本 index.html（版本目录机制）
     引导用户强刷（hash 资源不变则无需）
  3. 功能开关：
     关闭本次新增功能开关（feature flag），保留主体服务
  4. 数据库：
     **不执行结构回滚**（迁移遵守"先加后删"，旧代码兼容新结构）；
     若发生数据污染：从最近一次 mysqldump 恢复（RPO≤24h），恢复期间只读或停机公告
  5. 回滚验证：
     核心接口探活 + 5 条核心链路冒烟（注册登录/孩子档案/周视图/标记完成/后台登录）
     + Sentry 错误率回落基线 + 团长回访清单抽 3 项
  6. 通知机制：
     对内：发布群 + 团长同步（版本/原因/影响面/恢复时间）
     对外（必要时）：站内公告"系统维护升级中，部分功能短暂不可用"+ 客服口径模板
     事故口径：发生了什么/影响范围/当前状态/预计恢复/补偿方案

【预计耗时】服务端 5~10 分钟 + 前端秒级 + 验证 10 分钟；总 ≤20 分钟（不含数据库恢复；数据库恢复 ≤2h 另计）
【责任人】发布负责人（决策）+ 值班研发（执行）+ QA（验证）+ 团长（知情）
【演练要求】上线前走查一次（对照本模板逐项确认命令与路径）；首次生产回滚后补充演练记录
```

### 5.3 数据库回滚注意事项

1. **Prisma migrate 无自动 down**：结构变更靠"先加后删"两版本节奏 + 新代码向后兼容，实现"逻辑回滚"；禁止破坏性变更（DROP COLUMN/TABLE、窄化类型、加 NOT NULL 无默认值）与功能变更同版本上线。
2. **代码回滚 ≠ 数据回滚**：回滚到旧代码时，数据库已是新结构——旧代码必须能容忍新列/新表存在（只增不破坏原则保证）；回滚前在预发环境做一次"新库 + 旧代码"兼容验证。
3. **数据修复优先于结构修复**：数据错误用修复脚本（幂等、经评审）而非恢复全量备份；全量恢复是最后手段（RPO 24h，需公告）。
4. **软删除设计**（children/homeworks 均有 `deleted_at`）降低误删不可逆风险；refresh_tokens 可吊销，回滚后旧 Token 自然失效。
5. **迁移期间禁发布**：`migrate deploy` 执行中禁止同时 reload 应用；迁移失败现场保留，禁止自动重试与自动 down。

## 六、审核风险提示（提前告知，禁止等被拒才补救）

## 九、沙盒受控环境交付专项（本次交付目标一）

### 9.1 交付形态

- **形式**：内网可访问链接（沙盒服务器部署，Nginx + PM2 双实例 + MySQL，与生产同架构同形态，仅规模与密钥不同）。
- **HTTPS 必须**：拍照上传链路依赖安全上下文（相机权限），沙盒同样部署 HTTPS——内网 `mkcert` 自签名 CA（验收机安装根证书）或沙盒有公网 IP 时用真实域名 + Let's Encrypt；验收设备清单随交付附上。
- **AI Provider**：沙盒使用测试 Key 或 Mock 开关（测试方案 §1.4），避免真实计费与不确定性；交付前做至少 1 次全真链路抽样（Qwen-VL）验证主链路 ≤10s。
- **数据**：沙盒库独立，造数 ≥5 家长账号（含 1 个三孩账号）、≥10 孩子档案、≥100 条作业、覆盖 recognize_failed 等状态；**沙盒数据为脱敏假数据，禁止录入真实儿童信息**。
- **管理后台**：沙盒同站部署，验收管理员账号 1 个（下架功能走查）。

### 9.2 沙盒上线流程（与正式发布同流水线降配）
