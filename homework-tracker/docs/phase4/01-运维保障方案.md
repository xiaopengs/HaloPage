## 一、部署架构与容量规划

### 1.1 资源清单与部署拓扑

**资源清单（单机 MVP 基线）**：

| 资源 | 规格/数量 | 用途 | 预估月费 |
|---|---|---|---|
| 云服务器 ECS | 4C8G × 1 台（包年包月） | Nginx + PM2 双实例 + MySQL 8 同机部署 | ~300 元 |
| 系统盘 | 40~100GB SSD | 系统 + 日志 + 本地备份暂存 | 含在 ECS |
| 阿里云 OSS | 私有 Bucket × 1（标准存储） | 作业照片 + 数据库备份文件 | ~2~15 元（按量） |
| CDN | 按量 | 静态资源 + 图片缩略图分发 | ~10 元（按量） |
| 域名 | 1 个（已备案） | 站点访问 | ~5 元（60~80 元/年） |
| HTTPS 证书 | Let's Encrypt 免费证书 | 全站 HTTPS | 0 |
| Sentry | 免费档 | 前端 JS 错误监控 | 0 |
| 云监控/拨测 | 阿里云免费档 | 指标 + 可用性拨测 | 0 |
| 识别 API | Qwen-VL 主 + GPT-4o/Claude 备 + 百度 OCR 降级 | 拍照识别 | 60~300 元（按量） |
| **合计** | — | — | **约 380~630 元/月** |

**部署拓扑**（承接技术方案 §2.1 / 发布方案 §3.2）：

```
家长用户（手机/桌面浏览器）
   │ HTTPS（TLS 1.2+，HSTS）
   ▼
CDN（静态资源 hash 缓存；图片经签名 URL + OSS 图片处理参数取缩略图 w_400）
   ▼
Nginx（HTTPS 终止 + 静态资源 + /api 限流兜底 burst=20 + /admin IP 白名单 + HTTP 301 跳转）
   ▼
PM2 cluster（2 实例，max_memory_restart 600M）── Node.js 20 + Express + TS
   │                        ├── /api/v1/* REST API（JWT 鉴权 + 水平越权校验）
   │                        └── 识别执行器（分级超时 25s+25s+10s + 降级链 + 熔断）
   ├── MySQL 8（本机；连接池 10/实例；每日 03:00 mysqldump → OSS 保留 14 天）
   ├── 阿里云 OSS 私有 Bucket（STS 直传，服务端签名 URL 读取）
   └── 第三方：Qwen-VL（主）/ GPT-4o·Claude（备）/ 百度 OCR（降级）/ Sentry / 阿里云内容安全（建议接入）
```

**进程与端口**：Nginx 80/443 对外；Express 3000 端口仅本机回环；MySQL 3306 不对外（仅本机，或云数据库白名单）；SSH 仅限办公网/IP 白名单 + 密钥登录。

### 1.2 环境划分（四套，配置与密钥隔离）

| 环境 | 用途 | 监控配置 | 数据 |
|---|---|---|---|
| 开发 local | 研发自测（Docker MySQL + Mock Provider） | PM2 本地日志即可 | 假数据 |
| 测试 staging | QA 全量/兼容/性能/安全测试（独立子域名 + HTTPS + OSS 独立桶） | Sentry 测试 DSN + staging 拨测 | 脱敏造数 ≥5000 条作业、跨 8 周 |
| 预发 pre-prod | 发布前最终验证（同生产配置与制品） | 同生产监控最小集 | 脱敏子集或空库 |
| 生产 production | 正式服务（人工审批 + tag 触发） | 本方案第二章全套 | 真实数据（监护人代理模式） |

**环境隔离红线**（承接发布方案 §1.3）：生产密钥只存在于生产服务器与 CI production secrets；staging 用独立 Bucket/独立数据库/测试 Key；禁止一套 `.env` 通用；上线检查单第 2 项核验"staging 值零残留"。

### 1.3 容量基线与水位测算

**容量基线（验收门禁 PERF-06 口径）**：单机 4C8G + PM2 2 实例，支撑 **500 并发在线**（浏览 + 录入混合），持续 10 分钟错误率 <0.1%；核心 API P95 ≤500ms；周视图 P95 ≤800ms；首屏 FCP ≤2s（4G）。

**负载测算（按日活千级 + 晚间高峰）**：

| 维度 | 测算 | 说明 |
|---|---|---|
| 峰值并发 | 500 并发在线（门禁值）；日常预估 50~150 并发 | 家长核心场景为晚间 19:00-22:00，占全日流量约 60% |
| 峰值 QPS | 约 10~30 QPS（读多写少，读:写 ≈ 8:2） | 周视图单次聚合查询命中索引 `(child_id, week_start, weekday)`，无 7×N 次请求 |
| 识别负载 | 不计入核心并发 | 识别为异步 UX（前端 30s 上限），且限流 10 次/小时/用户；按日活 100 家长 × 2 次/天 ≈ 200 次/日 |
| DB 连接 | 池 10/实例 × 2 = 20 连接 | MySQL 8 默认 max_connections=151，余量充足 |
| 单实例承载 | 约 250 并发/实例 | PM2 cluster 双实例均分；单实例故障时另一实例顶住 50% 降级服务 |
| 内存预算 | 每实例上限 600M（`max_memory_restart`）+ MySQL Buffer Pool ~2G + Nginx/系统 ~1G | 8G 总内存的常规分配；PM2 超限自动重启自愈 |

**容量水位分区**：

| 区间 | CPU（晚高峰均值） | 内存 | 磁盘 | P95 | 动作 |
|---|---|---|---|---|---|
| 绿区 | <60% | <70% | <70% | ≤基线 | 常规巡检 |
| 黄区 | 60%~80% | 70%~85% | 70%~85% | ≤基线 1.5 倍 | P2 告警；进入扩容评估；输出容量报告给增长运营师 |
| 红区 | >80% 持续 10min | >85% | >85%（>92% 为 P0） | >基线 2 倍持续 10min | P1/P0 告警；48 小时内执行扩容或限流兜底 |

### 1.4 扩容触发条件与路径

**触发条件（满足任一即启动评估，满足两项即执行）**：

1. 工作日 19:00-22:00 CPU 均值 >70% 连续 3 天；
2. 内存 >80% 连续 3 天（排除内存泄漏因素后）；
3. 核心 API P95 连续 3 天 >基线 1.5 倍（如 >750ms）；
4. 500 并发压测错误率 >0.1%，或性能拐点并发 <500；
5. 磁盘按当前增长速度预计 3 个月内写满；
6. 大促/裂变活动前，增长运营师提供活动量级超出基线 2 倍以上（按参考文件第十章协作要求，活动前必须做容量评估）。

**扩容路径（按序升级，不跳级）**：

| 级别 | 动作 | 适用场景 | 预计耗时 | 风险 |
|---|---|---|---|---|
| L1 配置优化 | Nginx 缓存/gzip 调优、慢查询治理、图片处理参数收紧 | 黄区初期 | 1 个发布窗口 | 低 |
| L2 垂直扩容 | ECS 4C8G → 8C16G（云厂商在线升配或低峰迁移） | 日活 1k~1w，黄区持续 | 30 分钟~2 小时 | 低（需停机或热迁移窗口） |
| L3 数据库独立 | MySQL 迁云 RDS（高可用版），释放应用机内存/CPU | DB 成为瓶颈 | 半天（迁移+DNS/连接串切换） | 中（需备份先行 + 割接演练） |
| L4 水平扩展 | SLB + 2 台应用服务器 + RDS 主从 + 引入 Redis 缓存 | 日活 >1 万（V1.2+ 架构演进） | 1~2 天 | 中高（架构变更，需研发介入） |

**降额路径**：日活连续 30 天 <100 且 CPU 均值 <30% → 降配节省成本（每月账单盘点时评估）。

**临时兜底**：发布日/活动日预期超载时，提前 1 天完成 L2 升配并在活动后 3 天内降回，控制成本。

## 二、监控告警体系

> 原则：监控**四层齐备**（基础设施 / 应用 / 业务 / 第三方依赖），只有资源层的方案视为不合格。识别服务作为本产品核心差异化能力，在第三方依赖层单列重点监控。

### 2.1 监控分层总览

| 层 | 关注问题 | 覆盖内容 | 采集方式 | 存储位置 | 看板入口 |
|---|---|---|---|---|---|
| L1 可用性层 | 服务死没死 | 拨测探活、HTTP 可用率、PM2 实例状态、证书/域名/备案状态 | 阿里云站点监控拨测（1 分钟）+ PM2 + certbot 检查 | 云监控 + PM2 日志 | 云监控控制台 + PM2 status |
| L2 性能层 | 服务卡不卡 | 接口响应 P50/P95/P99、慢查询、资源水位（CPU/内存/磁盘/连接数）、识别链路耗时 | 应用中间件埋点 + MySQL 慢日志 + 云监控 Agent | 云监控 + `/var/log/homework-tracker/` + Sentry | 云监控 + 管理后台数据看板（B-01） |
| L3 业务层 | 生意好不好 | 注册数、WAP（北极星 homework_create）、作业条目量、注册→首条作业转化率、识别确认率、上传成功率、次周回访率 | 埋点事件 + 定时任务查库生成日报 | MySQL + 日报（管理后台 B-01） | 管理后台数据看板 + 每日业务日报（IM/邮件） |
| L4 第三方依赖层 | 依赖掉不掉 | **识别服务（重点）**、OSS/STS、Sentry、CDN、阿里云内容安全（如接入） | 应用侧 Provider 封装计数 + 云服务控制台 | recognition_tasks 表 + 应用日志 | 识别服务监控看板（B-01 已有规划）+ 成本看板 |

| MySQL 连通性 | 应用 health 端点内含 DB ping | 正常 | AL-04 |

### 2.5 第三方依赖层指标（L4）—— **识别服务是监控重点**

**识别服务监控（Qwen-VL 主链路为核心）**：

| 指标 | 采集方式（recognition_tasks 表 + Provider 封装计数） | 目标/基线 | 告警联动 |
|---|---|---|---|
| Qwen-VL 调用成功率 | `provider='qwen'` 成功/总数（5 分钟窗口） | ≥95%；**失败率 >20% 持续 10 分钟 = 熔断触发条件** | AL-15 |

1. **每条告警必须可执行**：告警文案模板固定为"【级别】【服务】指标当前值 vs 阈值 + 建议动作 + Runbook 链接"，禁止"收到告警后人工排查"式空动作；

### 2.8 日志与可观测性规范

1. **日志三分类**：
   - 访问日志（Nginx：来源/路径/状态码/耗时）；
   - 应用日志（业务事件：关键动作用 INFO，可预期异常用 WARN，需人处理用 ERROR）；
   - 审计日志（登录、注销、权限变更、后台下架、数据导出，留存 ≥6 个月）。
2. **结构化输出**：JSON 统一字段（timestamp/level/service/trace_id/message），禁止纯文本自说自话；
3. **trace_id 贯穿**：一次请求从 Nginx → Express → 识别 Provider 共享 request_id，排障一查到底；
4. **脱敏红线**：日志禁止输出手机号全文（脱敏 138****0001）、密码、完整 token、`PHONE_ENC_KEY`；识别请求的图片 base64 不得落日志；
5. **保留周期**：应用日志 ≥14 天可检索（logrotate 按日切割、gzip 归档），归档 ≥90 天（转 OSS 低频存储）；磁盘水位与保留策略联动（AL-10/AL-10b），防止日志写满磁盘触发新故障；
6. **日志位置**：`/var/log/homework-tracker/{out,error}.log`（PM2）+ Nginx access/error log + Sentry（前端）。

## 三、稳定性保障

### 3.1 SLO/SLA 定义

**对内 SLO（稳定性目标，按月统计）**：

| SLO 指标 | 目标值 | 统计口径 | 度量方式 |
|---|---|---|---|
| 站点可用性 | **≥99.5%**（月停机预算 ≈3.6h） | 用户侧失败请求数/总请求数（5xx + 拨测失败 + 超时 >30s），非服务器进程存活 | 云监控拨测（1 分钟）+ 网关 5xx 聚合，取两者差集 |

| 周视图性能 | P95 ≤800ms | week-view 接口（含 50 条/周大数据量场景） | 同上 |
| 上传成功率 | ≥99% | 压缩后 ≤1MB 图片直传成功/发起 | 埋点 + OSS 上传回调 |
| 识别主链路 | 单次 P95 ≤10s | Qwen-VL 单次成功耗时（BQ-03） | recognition_tasks.duration_ms |
| 识别可用性 | 三级链任一可用即可完成；全链路不可用 ≤30 分钟/月 | 三级整体成功率 ≥98% | recognition_tasks 聚合 |
| 前端稳定性 | JS 错误率 ≤0.5% PV；白屏/卡死率 =0 | Sentry PV 口径 | Sentry + 兼容矩阵 |
| 数据持久性 | RPO ≤30min（增强）/24h（基础）；RTO ≤2h | 备份恢复演练实测 | 演练记录 |

**对外 SLA（如向用户承诺，承诺值低于实际能力）**：

| 级别 | 可用性承诺 | 月停机预算 | 说明 |
|---|---|---|---|
| 本产品对外承诺 | **99.0%** | ≈7.2h | 家长晚间使用为主，单机架构；承诺值低于内部 SLO 99.5%，预留缓冲 |
| 内部目标 | 99.5% | ≈3.6h | 对齐技术方案非功能性承诺 §11 |
| 识别服务 | 不单独承诺可用性（第三方依赖），承诺"识别失败必有人工兜底，功能闭环不断点" | — | 对齐 PRD 兜底设计 |

**SLA 配套**：
- "不可用"统计口径：以**用户侧错误率**为准（连续 5 分钟 >5% 请求失败或拨测失败计为一次不可用事件），而非服务器进程存活；
- 度量方式：第三方拨测数据（阿里云站点监控）+ 网关日志双源交叉验证，每月出具《可用性报告》；
- 补偿条款：MVP 自用/小范围阶段不涉及赔付；若未来商业化，按承诺值协商补偿。

### 3.2 限流、熔断、降级策略（与识别降级链逐级对齐）

**限流策略（三层防线）**：

| 层 | 对象 | 阈值 | 动作 |
|---|---|---|---|
| Nginx | 全局限流兜底 | `limit_req zone=api burst=20 nodelay` | 429 + 重试提示 |
| 应用-登录 | 登录/注册 | 5 次/分/IP | 429/1004 + 通用文案（防账号枚举） |
| 应用-识别 | 识别触发 | 10 次/小时/用户 | 429/1004 + "识别太频繁，请稍后再试或手动录入" |
| 应用-全局 | 全部 API | 100 req/分/IP | 429/1004 + 日志记录 |
| 应用-状态机 | recognize 幂等 | recognizing 中拒绝重复；同 image_hash 复用成功结果 | 防重复计费与脏状态 |

**熔断策略（识别链路）**：

| 熔断器 | 触发条件 | 熔断动作 | 恢复条件 |
|---|---|---|---|
| 主 LLM 熔断（Qwen-VL） | 连续 10 分钟失败率 >20% | 后续请求直接走备用 LLM，不再尝试主链路 | 熔断 5 分钟后半开探测：放 10% 请求试探，成功率 ≥90% 则恢复 |
| 备用 LLM 熔断 | 备用 LLM 连续 10 分钟失败率 >20% | 降级至百度 OCR | 同上半开探测 |
| OCR 熔断 | OCR 连续失败率 >50% | 全部转手动录入兜底 | 人工确认服务恢复 |

**降级策略表（对齐技术方案 §4.7，与监控告警一一对应）**：

| 触发条件 | 自动动作 | 用户可见结果 | 对应告警 |
|---|---|---|---|
| 主 LLM 超时/5xx（单次，25s） | 切备用 LLM | 无感知 | AL-17 |
| 主+备 LLM 均失败 | 切百度 OCR（10s，印刷体模式） | 提示"已切换基础识别模式"，学科需用户选择 | AL-17/18 |
| OCR 也失败/图片不可读 | status=recognize_failed | 明确提示"识别失败，请手动输入"，照片保留 | AL-19 |
| LLM 连续 10 分钟失败率 >20% | 熔断标记，后续直接走 OCR | 提示基础识别模式 | AL-18 |
| 单用户识别 >10 次/小时 | 限流 429 | "识别太频繁，请稍后再试或手动录入" | AL-29 |
| 月识别成本超预算 200% | 人工调低模型档位/收紧限流 | 无感知 | AL-30 |
| 直传 OSS 失败率升高 | 切换服务端代理上传（POST /upload/proxy） | 仅感知为重试/稍慢，照片不丢 | AL-13/14 |
| 相机权限被拒/不可用 | 相册入口 → 手动录入 | 引导文案明确，闭环不断点 | 兼容测试口径 |
| 流量洪峰 | 限流 + 队列削峰（识别异步）+ 静态资源 CDN 兜底 | 核心浏览可用，写操作可排队/稍候 | AL-25/26 |
| DB 压力过大 | 限流保护数据库（全局 100 req/分/IP 收紧至 50） | 部分写操作稍候 | AL-11/12 |

**容量保护红线**：任何降级都不允许把用户数据置于丢失风险（软删除设计 + 本地草稿自动重试 3 次 + 照片保留为附件）；任何限流不允许阻断"手动录入"这条兜底闭环。

### 3.3 数据备份与恢复策略（RPO/RTO）

**备份策略表**：

| 对象 | 策略 | 频率 | 保留周期 | 存放 |
|---|---|---|---|---|
| MySQL 数据库 | mysqldump 全量（含 routines/events，`--single-transaction`） | 每日 03:00 | **≥14 天**（重要数据 30 天：月初全量单独标记保留） | OSS 独立 Bucket 前缀 `backup/mysql/`（与生产桶隔离） |
| MySQL binlog（增强项） | 实时增量归档 | 持续 | 7 天 | 同 OSS 前缀 `backup/binlog/` |
| 作业照片（OSS） | 版本控制开启 + 跨区域只读复制（可选增强） | 持续 | 与主数据一致 | 阿里云 OSS 私有 Bucket |
| 配置与密钥 | 配置仓库（脱敏模板）+ 服务器 env 文件（600 权限）+ 云 KMS | 每次变更留版本 | 永久 | 代码仓库（脱敏）+ 服务器 |
| 代码与制品 | Git 远程仓库（含 tag）+ CI 制品库 | 每次发布 | 制品保留最近 10 个/30 天；代码永久 | GitHub + Artifact |
| 审计日志 | DB 表 + 日志归档 | 持续 | ≥6 个月 | MySQL + OSS 归档 |

**RPO/RTO 目标**：

| 指标 | 基础方案（每日全量） | 增强方案（加 binlog 增量） |
|---|---|---|
| RPO（数据丢失窗口） | ≤24h | **≤30min** |
| RTO（恢复耗时） | ≤2h（全量恢复 + 验证） | ≤2h |

**说明**：MVP 阶段先落地基础方案（上游技术方案口径）；上线后 1 个月内评估开启 binlog 增量归档（成本几乎为零，RPO 从 24h 降至 30 分钟），作为稳定性增强项排入 V1.1。发布窗口的增量风险由"迁移只增不破坏 + 软删除设计 + 发布前强制 mysqldump"兜底。

**恢复演练要求（没有验证过可恢复的备份等于没有备份）**：

| 项 | 要求 |
|---|---|
| 演练频率 | **每季度至少 1 次**从备份拉起完整恢复演练（含一次"备份 → 新实例 → 数据校验 → 应用连通"全流程） |
| 演练记录 | 记录实测 RTO/RPO、失败步骤、改进项；写入《运维演练报告》归档 |
| 首次演练 | **上线后 30 天内必须完成首次演练**（不等季度） |
| 演练方式 | 沙盒/测试库执行，禁止在生产库演练；校验行数、抽 10 条业务数据比对、应用连通性 |
| 失败处置 | 演练失败 = P1 故障，24 小时内修复备份链路并重新演练 |

**备份成功核验（每日）**：09:00 自动检查 OSS 是否存在当日备份文件且大小 >0 并与昨日偏差 <20%；失败即 AL-34。

> 通用纪律（承接参考文件 3.2）：**先止血后查因**；5 分钟内给出初步判断（影响面 → 最近变更？依赖正常？资源异常？）；确认是变更引起的直接回滚，不在故障高峰期排查根因。

**E-01 服务宕机（PM2 实例异常 / 应用进程退出）**

- **判断标准**：拨测失败（AL-01）；`pm2 status` 实例 <2 或全部 offline；Nginx 502/504 突增。
- **恢复步骤**：
  1. `pm2 status` 确认实例状态；`pm2 logs --lines 100` 看崩溃前最后日志（OOM/未捕获异常/端口占用）；
  2. 单实例崩溃：`pm2 reload homework-tracker` 零 downtime 恢复，确认另一实例承载期间错误率；
  3. 全部崩溃：`pm2 restart homework-tracker` → 仍起不来：检查端口/磁盘/env 文件 → 回滚到上一稳定版本目录（`ln -sfn` + `pm2 reload`，5~10 分钟，衔接发布方案 5.2）；
  4. Nginx 异常：`nginx -t && systemctl reload nginx`；配置错误回滚上一版配置；
  5. 验证：`curl https://域名/api/v1/health` + 5 条核心接口探活 + 拨测恢复确认；
  6. 持续观察 30 分钟错误率回落。
- **责任人**：值班运维（执行）、发布负责人（回滚决策）。
- **预防**：PM2 `max_memory_restart 600M` 自愈、`pm2 save && pm2 startup` 开机自启、发布窗口避开高峰。

---

**E-02 整机故障（ECS 宕机 / 需要重启）**

- **判断标准**：SSH 无法连接 + 拨测失败 + 云监控无 Agent 心跳。
- **恢复步骤**：
  1. 云控制台重启实例/强制重启；等待 3~5 分钟；
  2. 确认开机自启生效（Nginx + PM2 + MySQL 均自动拉起）：`systemctl status nginx mysql` + `pm2 status`；
  3. 未自启则按序手动拉起；检查文件系统（`fsck` 提示/只读挂载）；
  4. 拨测 + 核心接口验证；核对最近一次备份完好（防数据损坏）；
  5. 若硬件故障需迁移：按 L3 路径在新机部署（制品 + 最新备份恢复），DNS/域名切换；全程 ≤2h（RTO 口径）。
- **责任人**：值班运维。
- **预防**：云盘快照每周 1 次；开机自启配置纳入上线检查单；关键配置入仓库。

---

**E-03 数据库故障（MySQL 不可用 / 连接打满 / 慢查询拖垮）**

- **判断标准**：AL-04 告警；应用日志大量 `ECONNREFUSED`/`ER_CON_COUNT_ERROR`；`SHOW PROCESSLIST` 大量 Sleep/Query 堆积。
- **恢复步骤**：
  1. `systemctl status mysql` 确认进程；挂了则重启并看 error log（磁盘满是首因，转 E-12）；
  2. 连接打满（AL-12）：`KILL` 非活跃连接 + `pm2 reload` 回收连接池；核查 Prisma 池配置与连接泄漏代码；
  3. 慢查询拖垮（AL-11）：`pt-query-digest`/慢日志找 Top SQL，`KILL` 长事务；写入限流收紧至 50 req/分/IP 保护 DB；
  4. 数据文件损坏：从最近一次 OSS 备份恢复（≤2h RTO），恢复期间站内公告"数据维护中"，恢复后核对行数与抽验；
  5. 验证：health 端点 DB ping 正常 + 周视图查询正常。
- **责任人**：值班运维（恢复）、研发（慢查询优化）。
- **预防**：慢日志常开、连接池监控、每日备份成功核验、发布前强制 mysqldump。

---

**E-04 数据库误删数据（人为或程序 bug）**

- **判断标准**：用户反馈数据丢失 / 后台发现记录异常缺失 / 误操作反馈。
- **恢复步骤**：
  1. **立即冻结写入**（开启维护页或只读模式），防止覆盖备份后数据；
  2. 评估删除范围（表/用户/时间范围）与最近备份时间点，计算数据丢失窗口（RPO）；
  3. 软删除表（children/homeworks 有 `deleted_at`）：优先用 `UPDATE ... SET deleted_at=NULL` 恢复，零丢失；
  4. 硬删除/无软删标记：从最近全量备份恢复到**临时库**，抽提缺失数据回灌生产（禁止直接全量覆盖生产，避免覆盖备份后的新数据）；
  5. 有 binlog 增量（增强方案）：按位点/时间解析 binlog 补录，RPO ≤30min；
  6. 数据核对（行数 + 抽 10 条业务比对）后恢复写入；通知受影响用户。
- **责任人**：值班运维（执行）、研发（脚本评审，修复脚本必须幂等且经评审）。
- **预防**：软删除设计、敏感操作二次确认、后台操作全量审计、备份可恢复演练。

---

**E-05 OSS/直传异常（STS 签发失败 / 直传成功率下降）**

- **判断标准**：AL-13/AL-14 告警；用户反馈上传失败；`/upload/credential` 5xx 增多。
- **恢复步骤**：
  1. 阿里云控制台核查 OSS 服务状态、RAM 角色与 AccessKey 有效性、Bucket 权限；
  2. STS 签发失败：检查 RAM 角色信任策略与 `OSS_RAM_ROLE` 配置；AccessKey 失效则轮换（热轮换，发布方案 3.5 口径）；
  3. 直传成功率下降：应用侧打开服务端代理上传降级开关（`POST /upload/proxy`），带宽成本换可用性；前端对用户仅表现为"重试/稍慢"；
  4. OSS 区域故障：如有多区域 bucket 配置则切换 endpoint；无则公告上传暂停、已传数据不影响查看；
  5. 验证：抽 3 个账号走完整上传链路。
- **责任人**：值班运维。
- **预防**：STS 权限最小化（前缀+15 分钟）、降级通道常备可用（测试方案 TC-UP-007 已覆盖）、OSS 与主备份桶隔离。

---

**E-06 识别服务全挂（三级降级链全部失败）**

- **判断标准**：AL-18 熔断触发且 AL-19 总成功率 <90% 持续 30 分钟；recognition_tasks 连续失败；用户反馈"识别一直失败"。
- **恢复步骤**：
  1. 确认三级链路状态：DashScope 控制台（Qwen-VL 服务/账户余额/限流）→ 备用 LLM Key 状态 → 百度 OCR 配额；
  2. **立即关闭识别入口**（配置开关）：上传后直接进入"手动录入 + 照片存档"模式，功能闭环不断点（发布方案 5.2 回滚条件第 5 条前半段）；前端文案"识别服务维护中，您可手动录入，照片已保存"；
  3. 账户欠费：立即充值（AL-30 预防性余额告警 <100 元）；
  4. 服务商故障：切换 Provider 主备顺序（Provider 抽象支持配置化切换）；评估启用备用供应商账号；
  5. 服务恢复后：半开探测（放 10% 请求）→ 成功率 ≥90% 恢复主链路 → 重新打开识别入口；
  6. 超过 2 小时未恢复：评估回滚至上一稳定版本（如故障与最近发布相关）。
- **责任人**：值班运维（切换）、研发（Provider 配置）。
- **预防**：三级降级链 + 熔断半开、手动兜底闭环、成本与余额告警、每周 1 次全真链路抽样（QA 口径）。

---

**E-07 HTTPS 证书过期/异常**

- **判断标准**：AL-21/22 告警；浏览器提示证书错误；拨测 SSL 握手失败。
- **恢复步骤**：
  1. `openssl s_client -connect 域名:443` 确认证书状态与剩余天数；
  2. 手动续期：`certbot renew --force-renewal && systemctl reload nginx`；
  3. 续期失败（ACME 校验问题）：检查 80 端口可达与 DNS 解析；切换 DNS-01 校验或备用 CA；
  4. 极端情况（<1 天且续期失败）：启用预置备用证书（签发时保留一份离线副本），先恢复服务再排查续期链路；
  5. 多域名核对：`openssl s_client` 逐域名（含 www/后台子域）验证，防漏配；
  6. 对外公告影响窗口（如曾中断）。
- **责任人**：值班运维。
- **预防**：certbot 自动续期 cron（每日 03:30 dry-run）+ 30/7/1 天三档告警（AL-20/21/22）+ fullchain.pem 部署规范。

---

**E-08 流量洪峰（突发流量/被推广/活动引流）**

- **判断标准**：QPS 超基线 3 倍且持续上升；CPU >80%（AL-05）；接口 P95 劣化（AL-07）；错误率上升。
- **恢复步骤**：
  1. Nginx 层收紧限流（burst 下调）+ 应用层全局 100→50 req/分/IP，保核心浏览；
  2. 识别请求天然异步 + 10 次/小时/用户限流，自动削峰；队列化排队（进程内异步）；
  3. 静态资源全部 CDN 兜底，确认命中率，降低回源；
  4. 非核心接口降级：关闭统计类/非 P0 接口（如 stats/overview）保核心闭环；
  5. 30 分钟内未回落：L2 临时升配（4C8G→8C16G），高峰后降回；
  6. 与增长运营师核对是否活动引流导致，评估容量预警流程改进（上游协作口径）。
- **责任人**：值班运维（限流）、发布负责人（升配决策）。
- **预防**：活动前容量评估（增长运营师输入）、限流参数演练、CDN 预热。

---

**E-09 遭受攻击（DDoS / 暴力破解 / 恶意刷量识别）**

- **判断标准**：AL-24 登录失败突增；单 IP QPS 异常；识别接口被刷（AL-29）；云监控流量异常。
- **恢复步骤**：
  1. DDoS/大流量攻击：启用阿里云 DDoS 基础防护 + 安全组临时收紧（仅放行 80/443 已知业务 IP 段视情况）；联系云厂商；
  2. 暴力破解：确认登录限流生效（5 次/分/IP）；Nginx/安全组封禁恶意 IP；审计日志核查有无登录成功异常记录；
  3. 识别刷量：收紧识别限流（10→5 次/小时/用户）+ 封禁异常账号；核查成本看板（AL-30）；
  4. 疑似数据泄露（越权成功/密钥泄露）：**立即按 P0 处置**——轮换相关密钥（JWT Secret/OSS AccessKey/PHONE_ENC_KEY）、封禁越权路径、固定证据（日志快照）、同步团长与用户，按合规要求评估是否履行告知义务；
  5. 事后：补充 WAF 规则、完善审计、更新安全基线。
- **责任人**：值班运维（处置）、团长（对外与合规决策）。
- **预防**：接口鉴权 100% + 水平越权校验（SEC-01/02 门禁）、限流三层防线、密钥定期轮换（每半年）、gitleaks 卡点。

---

**E-10 磁盘写满（日志/备份/数据增长）**

- **判断标准**：AL-10b 磁盘 >92%；`df -h` 100%；MySQL 报 `No space left`。
- **恢复步骤**：
  1. `du -sh /* | sort -rh | head` 定位大户（通常是日志/备份/PM2 out.log）；
  2. 清理：`pm2 flush` + logrotate 强制轮转 + 删除 14 天前本地备份（OSS 已有）；
  3. MySQL 若已停：清理空间后重启并做一次一致性检查；
  4. 应急转储：大文件先传 OSS 再删；
  5. 验证：df <80% + health 正常；
  6. 根治：调整日志保留策略、升级磁盘（L2 扩容时一并）、OSS 生命周期规则核查。
- **责任人**：值班运维。
- **预防**：logrotate 按日切割 + gzip、备份文件只留本地 1 份、磁盘三档告警（75/85/92%）。

---

**E-11 第三方依赖故障通用预案（CDN / Sentry / 内容安全服务）**

- **判断标准**：AL-32/AL-33 告警；云厂商服务状态页公告。
- **恢复步骤**：
  1. CDN 故障：切换回源直连（临时关 CDN 指向源站），静态资源可承受；
  2. Sentry 故障：前端错误采集降级为本地日志轮转（不影响业务，仅影响可观测性）；
  3. 内容安全服务（绿网）故障：**切换人工审核兜底**（合规义务不可中断），未审核 UGC 阻断 C 端展示，后台标记待审；
  4. 任一第三方故障超过 SLA 预期：启用备选供应商（如 COS 备选）或书面豁免 + 人工兜底。
- **责任人**：值班运维。
- **预防**：核心链路不依赖非必要第三方（识别降级链即此设计）、兜底通道常备、内容安全"机器+人工"双轨。

---

**E-12 备份失败/不可恢复**

- **判断标准**：AL-34 备份任务失败或 OSS 无当日文件；季度演练失败。
- **恢复步骤**：
  1. 当日失败：查 cron 执行记录与错误输出（磁盘满/凭证过期/OSS 权限）；
  2. 手动补备：`mysqldump --single-transaction | gzip` 上传 OSS 并校验文件完整性（大小+解压测试）；
  3. 连续 2 天失败：升级 P0，排查备份链路全环（cron→脚本→凭证→OSS）；
  4. 演练失败：24 小时内修复并重新演练，记录改进项。
- **责任人**：值班运维。
- **预防**：每日 09:00 自动核验备份文件、备份与生产桶隔离、每季度演练 + 上线后 30 天内首演。

### 4.4 故障处理流程（发现 → 定位 → 恢复 → 复盘）

1. **发现**：监控告警 / 用户反馈（C 端反馈入口 P-09）/ 巡检发现，任一来源进入同一处理通道（IM 值班群 + 故障单）；
2. **定位（5 分钟内初步判断）**：明确影响面（哪些用户/功能/是否涉及儿童数据）→ 三连问（最近变更？依赖服务正常？资源异常？）→ 先止血后查因，变更引起直接回滚；
3. **恢复**：按对应预案执行；恢复后 30 分钟观察窗确认指标回落；
4. **复盘（48 小时内，不追责、追流程）**：
   - 四要素：时间线（发现/响应/恢复各时点）、根因（直接+深层）、影响面（用户量/时长/数据）、改进项（每项有责任人与截止时间）；
   - 同类事故不得二次发生；改进项进需求池跟踪；
   - P0/P1 复盘报告归档（保留 ≥1 年）。

### 4.5 值班机制

- **7×12 值班**（08:00-22:00 覆盖家长使用时段；22:00-08:00 仅 P0 电话响应）；
- 每周排定"第一响应人 + 备份人"，联系方式置顶 IM 群；
- **P0 预案打印/文档置顶**：故障时不需要现想（本方案 4.3 十二项预案即为该文档）；
- 每次交接班核对：未闭环告警、进行中故障、待观察项；
- 值班记录（认领时长/恢复时长）纳入月度运维报告，驱动流程改进。

### 5.2 儿童数据特别措施（合规红线）

- 数据最小化：仅手机号/邮箱 + 孩子昵称/年级 + 作业照片（不收集身份证号/学校/住址/生日）；
- 注销通道：注销后 30 天内删除个人数据（含照片 objectKey 物理删除），运维侧每月核对注销工单闭环；
- 照片保护：私有 Bucket + 15 分钟签名 URL + 送模型走 base64 内联（不经公网 URL）；
- 泄露响应 SOP：疑似泄露立即 P0（E-09 步骤 4）→ 固定证据 → 轮换密钥 → 评估法定告知义务 → 48 小时内输出事件报告；
- 隐私政策/协议页（含儿童信息专门规则）随版本发布核验可访问性（上线检查单第 6 项）。

### 6.3 识别调用成本控制（关键项）

| 手段 | 做法 | 效果 |
|---|---|---|
| 输入瘦身 | 客户端压缩 ≤1MB（BQ-02 口径；长边 ≤1600px、JPEG 0.8） | 直接降低 token 计费；统一格式 |
| 按需触发 | 识别不自动跑，用户主动触发；取消可中断 | 避免无效调用 |
| 幂等复用 | 同 image_hash 已有成功结果直接复用（状态机保障） | 重复上传同图零成本 |
| 限流 | 10 次/小时/用户（429 明确文案引导手动录入） | 单用户成本封顶 |
| 熔断 | 主链路失败率 >20% 持续 10min 自动熔断走 OCR/手动 | 避免向故障服务持续付费 |
| 档位管理 | recognition_tasks 记录 provider/duration/confidence 形成成本看板；月成本超预算 200% 调低模型档位（如主链路切换更低价模型或提高压缩率） | 成本可控降级 |
| 余额预警 | <100 元告警（AL-30） | 防欠费停摆 |

**成本测算参考**：6000 次/月 × 0.01~0.05 元 = 60~300 元/月（选型报告口径）；若识别确认率持续 <55%（PRD 线），评估降级为"纯图片存档 + 手动录入"，识别成本可趋近于零——此为产品决策，运维提供数据支撑。

### 6.4 存储生命周期管理

| 数据 | 生命周期规则 | 理由 |
|---|---|---|
| OSS 作业照片 | 标准存储 → 创建 90 天后转低频访问（IA）→ 长期保留 | 家长数据不可删（儿童数据合规 + 注销才删）；历史周回看为低频读 |
| OSS 数据库备份 | 保留 14 天自动删除（规则：`backup/mysql/` 前缀，14 天）；月初全量标记保留 30 天 | 对齐技术方案保留口径；重要数据 30 天 |
| OSS binlog 归档（增强） | 保留 7 天自动删除 | RPO 增强项 |
| OSS 日志归档 | 保留 90 天自动删除 | 审计日志 ≥6 个月部分留 DB |
| ECS 本地日志 | logrotate 按日切割、gzip、保留 14 天 | 防磁盘写满（E-10） |
| ECS 本地备份 | 仅留最近 1 份，上传 OSS 后即删本地 | 双保险不占磁盘 |

## 七、运维 Runbook

### 7.1 日常巡检清单

**每日（约 15 分钟，建议 09:00）**：

### 7.2 发布日运维配合（衔接发布方案第七章）

**发布前 1 个工作日**：

- [ ] 确认发布单（版本/时间窗/责任人/回滚预案）已发出并确认；
- [ ] 确认质量门禁 G1~G12 放行结论（《测试报告》出具"放行"）；
- [ ] 回滚走查：上一稳定版本制品在位；回滚命令与路径演练一遍（发布方案 5.2）；
- [ ] 监控就绪：拨测/告警通道/值班表确认；发布窗口期（10:00-11:00 + 其后 2h）联系人在岗（发布负责人/值班研发/QA/团长）；
- [ ] 容量确认：当前水位在绿区；预期无冲突活动。

**发布窗口（工作日上午 10:00-11:00，严禁 19:00-22:00）**：

```bash
# 标准发布动作（承接发布方案 3.3）
# 1. 迁移前强制备份
mysqldump -h*** -u*** homework_tracker | gzip > /tmp/pre-{版本}-$(date +%F).sql.gz
# 2. 迁移（仅向后兼容）
cd server && npx prisma migrate deploy
# 3. 切版本目录 + reload
ln -sfn /opt/homework-tracker/releases/{版本} /opt/homework-tracker/current
pm2 reload homework-tracker --env production
# 4. 冒烟
./scripts/smoke.sh https://域名     # health + 5 核心接口 + 首页 200
# 5. 前端静态切换（CDN 版本目录或 Nginx root 软链）
```

- 运维值守要点：备份文件确认落 OSS；migrate 失败现场保留（禁自动重试/down）；reload 期间观察 PM2 逐个重启无报错；冒烟 6 项全过；
- 回滚触发（任一）：核心接口错误率 >1% 持续 5min / P0 bug / JS 错误率 >0.5% PV / 转化跌幅 >20% / 上传 <99% 或识别全链路不可用 >30min / 安全事件 → 5 分钟内启动回滚（发布方案 5.2 模板，服务端 5~10min + 前端秒级，总 ≤20min）。

**发布后**：进入 72 小时观察期（7.3）；发布材料 24h 内归档（发布单/制品记录/配置变更/观察报告，保留 ≥1 年）。

### 7.3 上线后 72 小时观察期运维要点（衔接发布方案第八章）

| 时点 | 检查项 | 通过标准 | 异常升级 |
|---|---|---|---|
| **T+30min** | 核心接口错误率、health 探活、上传成功率、识别调用量与耗时、JS 错误率 vs 基线 | 错误率 <1%；上传 ≥99%；JS 错误率 ≤0.5% PV | 触发回滚条件即按 5.2 回滚 |
| **T+2h** | Sentry 新增 issue；后台反馈/举报；**告警静默期核对**（AL-36，防通知通道故障） | 无 P0/P1 新增 issue | P0 立即回滚并同步团长与用户 |
| **T+24h** | 业务指标：注册数、WAP（homework_create）、作业条目量、注册→首条转化 ≥60%、识别确认率 ≥70%、客诉量 | 无异常波动；转化/确认率达标 | P1 → 24h 内热修或下个修订版 |
| **T+72h** | 发布复盘：清单执行偏差、告警调优（观察期误报漏报）、用户反馈 Top3 进需求池；输出《上线观察报告》 | 复盘完成并归档 | 观察项转入 V1.1 排期 |

**观察期特别盯守（家长晚间高峰 19:00-22:00）**：前 3 个晚间高峰时段值班人在线；重点看上传成功率、识别成功率与耗时、周视图 P95、5xx 比例；任何指标跌破 SLO 即按对应预案处置，不留过夜。

# 证书
openssl s_client -connect 域名:443 -servername 域名 2>/dev/null | openssl x509 -noout -dates
certbot renew --dry-run             # 续期演练

logrotate -f /etc/logrotate.d/homework-tracker
